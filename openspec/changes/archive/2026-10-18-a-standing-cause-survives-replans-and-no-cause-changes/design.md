## Context

`StoredUnit.cause` (`pipeline/unit_store.py`, a property) returns the `cause` of `history[-1]`, or none. Every writer that appends an entry with no cause therefore ends whatever cause stood, whether or not the situation did. Checked on the main branch:

- `_with_state` (the function at the end of `unit_store.py`) appends `{state, at}`. Its callers are `UnitStore.upsert`'s promotion of an `unplanned` unit and its demotion of a planned unit the plan omits, and `unplan_vanished`. `join` builds its own entry, `{state, at, note: "joined"}`, with no cause; it only touches unstarted units, so the loss is latent.
- `pipeline/events.py` writes `in_review` with no cause when a conflict move comes back `DEFERRED`, right after `restack` wrote `planned` with `restack_deferred` (five writes in `restack`, one more with `restack_conflict`).
- The reviewer's hold label (`events.py` on hold and on release, and the graph's own copy in `graph/nodes.py`) takes a unit with a pull request to `held` and back to `in_review` with cause `released`. Out of scope, see the end.
- `upsert` builds a fresh `StoredUnit` from the plan and copies about thirty fields from the stored record. Thirteen it does not copy are runtime state, not shape: `parked_splits`, `parked_sha`, `parked_snapshot`, `parked_attempts`, `service_attempts`, `gated_requeue`, `waited_on`, `wait_ended`, `close_pending`, `step`, `guidance`, `ready_at`, `first_human_activity_at`. The history is kept.
- `release_gated` clears `gated_requeue` and then rewrites the cause.

Causes fall in two classes. Standing: the cause names a situation that lasts until something changes it. Event: the cause names a transition that happened and is over. `Cause.USAGE` is in the enum and read once (`serve/chat.py`) and never written; it is standing, because a usage pause lasts the window.

| Class | Causes |
|---|---|
| Standing | `split_held`, `gated`, `upstream_went_back`, `base_changed`, `restack_deferred`, `restack_conflict`, `restack_handed_back`, `host_unavailable`, `network_unavailable`, `service_unavailable`, `environment`, `rework`, `usage`, `dirty_worktree`, `attached`, `needs_human`, `reviewer_hold`, `toolchain`, `depth`, `review_escalated_class`, `review_escalated_disagreement` |
| Event | `requeued`, `released`, `adopted`, `merged`, `auto_landed`, `closed`, `failed` |

## Decisions

- **Carry the previous cause forward; do not store a second `standing_cause` field.** A second field would need a schema change, a migration and the older-release refusal the store applies to unknown fields, and it would be a second place that can disagree with the history. The history stays the single source.
- **`KEEP`, a sentinel in `unit_store.py`.** A small class `Keep` with one instance `KEEP`. `set_state`, `_record_state` and `_with_state` take `cause: Cause | None | Keep`. The default stays `None`, so a caller that passes nothing still records no cause and `tests/pipeline/test_unit_causes.py` ("a state change without a cause records none, even after one with") still holds. `KEEP` is for the changes the store makes on its own account; a state change a caller records still passes its own cause, or none to end the standing one.
- **Resolution.** One helper builds a history entry: `_entry(unit, state, cause, note)`. With `KEEP` it resolves to `unit.cause` when that is in `STANDING_CAUSES`, and to no cause when it is an event cause or none. A resolved entry carries the previous entry's note unless a note is passed (`join` passes `joined`, which wins) and is marked `"carried": true`. An event cause is not carried: `requeued` on an `unplanned` unit would claim a requeue that is long over, and the skip log (`stopped for requeued`) would repeat it.
- **`STANDING_CAUSES` and `EVENT_CAUSES`.** Two frozensets beside `Cause`. A test requires that together they are exactly the members of `Cause` and disjoint, so a new cause cannot be added without being classified.
- **`cause_since`.** A property on `StoredUnit`: the `at` of the entry that set the current cause. It walks back from the latest entry over entries marked `carried` and returns the `at` of the first entry that is not (the entry that really set the cause), or none when there is no cause. The obvious definition, the first entry of the trailing run of the same cause, is wrong for a parking: a unit parked for the code host twice in a row has two identical entries in a row, and the second parking must restart the backoff. Only the `carried` mark tells a carry from a parking. History entries are free dicts that older releases do not validate, so the mark needs no schema change and an older release reading the file reads the carried cause as the latest cause, which is the intent.
- **`backoff_ends` reads `cause_since`** instead of `history[-1]["at"]`. `PARK_BACKOFF` is indexed by `parked_attempts` (`min(max(parked_attempts, 1), 5) - 1`), so group 2 matters here: until `upsert` carries `parked_attempts`, a replan resets it to 0 and the index falls to the first, one-minute step. A carried entry does not change the index.
- **`KEEP` is resolved before the `PARKED_CAUSES` checks in `_record_state`.** `step` is kept when the resolved cause is a parked cause, so a carried parking keeps its step. `parked_attempts` is incremented only when a parked cause was passed explicitly: a carry is not another parking. The check on `state in (IN_REVIEW, FAILED)` is unchanged. `_with_state` and `join` do not go through `_record_state`, so they touch no counter.
- **`_record_state` clears `gated_requeue` itself.** When the resolved cause is not `gated` it writes `gated_requeue = None` in the same `model_copy`, like its resets of `step`, `held_by` and `moved_base_run`. Every writer of a gate calls `set_state(..., GATED)` first and `set_gated_requeue` after (`cli/pipeline.py` requeue, `graph/nodes.py` `park_for_fix`, `pipeline/events.py` restack), so the order is safe. In `release_gated` the non-delivered path now rewrites the cause in one write and the delivered path keeps its explicit clear, because the thread's first state write is not under this function's control.
- **`_sent_back` is not triggered by a carried entry.** It compares the history length with the length when the pass started the unit, then looks at the cause. A started unit's latest entry is its `running` entry, which carries no cause, and `upsert` leaves a `running` unit's state alone; a carried entry is written only to a `planned` unit, whose latest cause already decided the question before the carry and decides it the same after. The one visible effect is the skip log, keyed on the latest entry's time: a carried entry would log the skip a second time. The key becomes `cause_since`, so it is logged once. A test pins both.
- **Decision sites.** The audit table below is the review of every reader of `cause`. Where the carry already makes a reader right, the change adds a regression test and no code; that is stated per site so nobody hunts for the missing edit.
- **`release_gated` and `awaits_release` key on the saved requeue.** A unit with `state == planned` and `gated_requeue is not None` is waiting to be delivered, whatever the cause says; the cause is no longer required. The waits (`waiting_on`, `awaiting_planning`) still gate the delivery. Because `_record_state` now clears the requeue whenever the cause is not `gated`, a requeue left beside another cause can only be an older record, and delivering it is what the person asked for.
- **The deferred conflict move writes `restack_deferred` explicitly** (one argument at the `in_review` write). This is the only writer that ended a cause the restack lane reads; `KEEP` is not used there because the cause was written by another function and the state moves from `planned` back to `in_review`, so naming it states the intent.
- **`abk status` "no recorded cause" lines stay,** for records from before causes were kept and for units whose cause an event or a caller ended. They are not removed: a held or started planned unit that really has none still needs a person's look. Fewer units will appear there, because a replan no longer puts them there.

### Overlap with unbuilt changes

- `a-started-unit-keeps-its-groups`, group 1, adds the missing `unstarted` guard to the demotion loop in `upsert`. This change does not duplicate it; it carries the cause across the demotion that guard still allows (an unstarted unit) and across the promotion.
- `a-dropped-unit-parked-on-a-split-takes-no-place`, group 1, carries `parked_splits`, `parked_sha`, `parked_snapshot` and `parked_attempts` in `upsert` and makes `in_progress` read `parked_splits`. This change carries all thirteen fields. They overlap textually only, there is no `Needs:` between them, and whichever builds second finds the fields already carried and drops its duplicate lines on rebase.
- `limits-split-into-global-and-project` modifies the requirement "A workspace bounds how many units are in progress". This change leaves that requirement alone and adds its own, so the two cannot clash at archive.

### Out of scope: a label hold ends a standing cause

The reviewer's hold label takes a unit with a pull request to `held` (`events.py`, the hold handler; `graph/nodes.py`, the thread's copy) and the release returns it to `in_review` with cause `released` (`events.py` on release; `graph/nodes.py`), whatever state it was in. A `planned` unit with a standing cause (for example `base_changed`) that a person holds by label and then releases comes back `in_review`, and its cause is gone. Returning it to `planned` with its cause carried is a behaviour question (does the label release resume a build?) and is not decided here.
