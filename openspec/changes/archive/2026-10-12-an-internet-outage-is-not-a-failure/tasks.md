# Tasks

Acceptance: none — an outage is faked in tier 1 (an injected runtime result, probe and clock); nothing a consumer drives changes, and a live outage must not be required to prove it.

Priority: 2

## 1. [agent-build-kit] [tier1] A network or provider outage parks the unit and does not fail it

Done when an agent run that ends on a DNS or connection failure raises `NetworkUnavailable`, the probe of the failed host plus a control group sorts the unit into `network_unavailable`, `service_unavailable` or an ordinary failure, the unit resumes at its step after the backoff, a failure for any other reason still fails the unit, and the status says which of the two the unit waits for. Estimate: about 530 changed lines.

- [x] 1.1 Test: `network_failure` says `strong` for text with `EAI_AGAIN`, `ENOTFOUND`, `ENETUNREACH`, `EHOSTUNREACH` or "temporary failure in name resolution", `weak` for "Can't reach the API server", `ECONNREFUSED` or "connect timed out" alone, and nothing for an HTTP 429, 500 or 529 text, a usage limit, a model refusal, and a text with a status code and a signature word together.
- [x] 1.2 Test: the claude runtime, given a run that exits 1 with the logged `API Error: Can't reach the API server — check your internet or DNS (EAI_AGAIN)` text, raises `NetworkUnavailable` carrying those words and the API host it called, and reports the call's spend through `on_result` first; the same exit with a model-refusal text returns `AgentResult(ok=False)` as before.
- [x] 1.3 Test: the ACP runtime, given a failed result whose text has a strong signature, raises `NetworkUnavailable`; a failed result with no signature returns `ok=False` as before.
- [x] 1.4 Test: the probe, with injected resolver and connect functions, reports for the API host and for the control group (the forge hosts and `limits.network_control_hosts`) whether each had a host that connected within the timeout, and reports the API host reachable when the probe itself raises or the control group is empty.
- [x] 1.5 Test: `classify_reachability` gives `network_unavailable` when the API host and the control group both fail, `service_unavailable` when the API host fails and one control host connects (the forge host alone being enough), and an ordinary failure when the API host connects or the probe errored.
- [x] 1.6 Test: a weak signature parks the unit by that classification and fails it with the error text and step when the API host connects or the probe errors; a strong signature parks it as `network_unavailable` whatever the probe says.
- [x] 1.7 Test: a unit whose implement step raises `NetworkUnavailable` ends `planned` with the cause `network_unavailable`, the step and the error text recorded, its branch, thread and saved feedback unchanged, its review, rework and check round counts unchanged, and it is not counted as failed in the tick's outcome; a weak signature with the control group up ends `planned` with `service_unavailable` the same way.
- [x] 1.8 Test: with a replaced clock, a parked unit of either cause is skipped, with the time remaining logged, until the backoff has elapsed (1, 2, 5, 10 then 30 minutes by consecutive parking, 30 thereafter), and is then readmitted and resumed at the step it stopped on; a unit parked for the code host reads the same table and still behaves as before.
- [x] 1.9 Test: a step that was continuing a session continues it on resume after a parking; a step that was not starts again; a parked unit with a branch still counts in `in_progress`, and a step that raises `HostUnavailable` still parks with `host_unavailable`.
- [x] 1.10 Test: the status prints `waiting for the network: <id> (<repo>) at <step>, <n>s remain — <note>` for `network_unavailable` and `waiting for the model service: <id> (<repo>) at <step>, <n>s remain — <note>` for `service_unavailable`, and keeps the code-host line for a host-parked one; the graph's and the unit page's label for the two causes differ.
- [x] 1.11 Test: `limits.network_probe_timeout_seconds` defaults to 5 and is refused at config load at 0, below 0 and when not a whole number with a message naming the key; `limits.network_control_hosts` defaults to `one.one.one.one` and `dns.google`, is refused when an entry is empty or carries a scheme or a path, and both are listed by `abk config --show`.
- [x] 1.12 Add `runtimes/network.py` (`network_failure` and its signature table), `NetworkUnavailable` in `runtimes/base.py`, the raise in `claude_code._finish` and in `acp`'s failed-result path, `pipeline/network_probe.py` with its injectable seam and `classify_reachability`, and the two limits in `LimitsConfig`.
- [x] 1.13 Add `Cause.NETWORK_UNAVAILABLE` and `Cause.SERVICE_UNAVAILABLE`, keep `step` and count `parked_attempts` for both, rename `HOST_BACKOFF` to `PARK_BACKOFF` and make `backoff_remaining` read all three causes, catch `NetworkUnavailable` beside `HostUnavailable` in the step handler, read the causes in `_sent_back` and the resume branch, and print the two status lines and labels.
- [x] 1.14 Document it in `docs/unit-graph.md` (the host-unavailable paragraph gains both causes and their labels), `docs/architecture.md` (the readmitted causes), `docs/agent-runtimes.md` (the typed error and what is and is not an outage) and `docs/configuration.md` (the probe timeout and the control hosts), update the `limits:` block of the `abk-config` skill and the `planned` row of the `abk-pipeline` skill, and add one bullet under `## Unreleased` as `AGENTS.md`'s Changelog section says.

## 2. [agent-build-kit] [tier1] A model service answering 5xx or 529 parks the unit, up to a cap

Done when a claude run whose closing status is 500 to 599 raises `ServiceUnavailable`, the unit parks with `service_unavailable` up to `limits.service_unavailable_attempts` times in a row and then fails, and every other status keeps failing the unit. Estimate: about 270 changed lines.

- [x] 2.1 Test: the claude runtime, given a closing event with `api_error_status` 529, 500 or 503, raises `ServiceUnavailable` carrying the status and the CLI's words and reports the call's spend through `on_result` first; with `api_error_status` null and the words `API Error: 529`, the same; with 401, 403, 404 or a model refusal it returns `AgentResult(ok=False)`; with 429 it raises `AgentRateLimited` as before; with no status in the event or the words it returns `ok=False`.
- [x] 2.2 Test: a unit whose step raises `ServiceUnavailable` ends `planned` with `service_unavailable`, the step and the error text recorded, its branch, thread, feedback and round counts unchanged, without asking the probe, and it is not counted as failed.
- [x] 2.3 Test: with `limits.service_unavailable_attempts` at 3, the third consecutive status parking parks and the fourth failure fails the unit with its error text and step; a completed step or a move to in review resets the count; parkings by the probe path do not count toward it and are not capped.
- [x] 2.4 Test: `limits.service_unavailable_attempts` defaults to 5, is refused at config load at 0, below 0 and when not a whole number with a message naming the key, and is listed by `abk config --show`.
- [x] 2.5 Add `ServiceUnavailable` in `runtimes/base.py`, the status reading in `runtimes/claude_output.py` (the structured `api_error_status` first, the CLI's words `API Error: <status>` only when it is null) and the raise in `claude_code._finish`, the `service_attempts` count on the unit and the cap in the step handler, and the limit in `LimitsConfig`.
- [x] 2.6 Document it in `docs/agent-runtimes.md` (the status rule and what is left as a failure), `docs/unit-graph.md` (the cap), `docs/configuration.md` and the `abk-config` skill's `limits:` block, and fold it into the changelog bullet group 1 added.

## 3. [agent-build-kit] [tier1] While the network is down, no agent run is started

Done when a parked network outage writes a `network` pause that stops a tick starting agent runs, the first tick whose control group is reachable clears it, a `service_unavailable` writes none, and the status shows it. Estimate: about 300 changed lines.

- [x] 3.1 Test: parking a unit as `network_unavailable` writes a pause marker of kind `network` with a reason naming the unit, and a second parking while it stands does not replace it with a later `until`; parking one as `service_unavailable` writes none.
- [x] 3.2 Test: with a `network` marker and a probe whose control group fails, a tick starts no agent run, logs once that it is waiting for the network and names the marker, and the unit's parked state is unchanged.
- [x] 3.3 Test: with a `network` marker and a probe whose control group connects, the tick clears the marker and starts ready units as usual, whatever the marker's `until`; a marker whose `until` has passed with the probe still failing stays.
- [x] 3.4 Test: a `usage` pause and a `rate_limit` pause behave as before, a `network` marker is not cleared by a usage reading that allows work, and `abk status` shows the pause as waiting for the network with its reason.
- [x] 3.5 Test: a unit that runs while the marker stands and fails for a reason of its own (no signature) still fails; with a `service_unavailable` unit standing and no marker, a tick starts ready units as usual.
- [x] 3.6 Add `"network"` to `PauseKind` and its writing and clearing in `pipeline/pause.py`, the probe-first check of the control group at the start of the tick in `cli/pipeline.py`, and the status line; read the tick's pause gate first and stop exactly what a `usage` pause stops.
- [x] 3.7 Document the pause kind in `docs/architecture.md` and the `abk-pipeline` skill's pause section, and fold it into the changelog bullet group 1 added.

## 4. [agent-build-kit] [tier1] A planning attempt is not spent on an outage, and a failed plan keeps its reason

Done when a planner call that ends on a network or service outage records the change as waiting with its attempt count unchanged, a tick plans it again after the backoff or once the network pause clears and plans nothing under the pause, an ordinary failure still counts and keeps a bounded, redacted reason, and `abk replan` and `abk status` say waiting, given up with the command to plan it again, or failing with the reason. Estimate: about 460 changed lines.

- [x] 4.1 Test: `plan_all` with a planner call that raises `NetworkUnavailable` records `ok: False`, `waiting: network`, `waits: 1`, `since`, `until` one minute on and the reason, leaves `attempts` as it was (0, and 1 for a record that had one failure on the same hash), stores no unit, and returns `PlanResult(status="waiting")`; three such calls with a replaced clock past each `until` leave `attempts` unchanged with `waits` 3 and `until` 1, 2 then 5 minutes on.
- [x] 4.2 Test: with the probe injected, a weak signature records a `network` wait when the API host and the control group fail, a `service` wait when the API host fails and one control host connects, and an ordinary failed attempt (attempts plus one, the reason kept) when the API host connects or the probe raises; a strong signature records a `network` wait whatever the probe says; a 429 (`AgentRateLimited`) is recorded as before and not as a wait.
- [x] 4.3 Test: a planner call that raises `ServiceUnavailable` records a `service` wait without asking the probe; with `limits.service_unavailable_attempts` at 3, the fourth consecutive one is recorded as an ordinary failed attempt with its reason and the wait is gone; waits from the probe path are not capped.
- [x] 4.4 Test: a record that waits with `until` ahead is skipped by `plan_all` (`skipped`, no planner call) and does not make `_needs_planning` true, so a round whose only candidate waits asks the usage guard nothing; once `until` has passed the change is planned, and a success removes `waiting`, `waits`, `since`, `until` and `reason` and keeps `attempts`; an ordinary failure on a waiting record ends the wait and adds one attempt; an edit of `tasks.md` starts the record over.
- [x] 4.5 Test: a tick with a `network` marker and a probe whose control group fails makes no planner call and records nothing for any change; with the marker and a control host connecting, the tick clears it and plans a change waiting for the network although its `until` is ahead; a `service` wait writes no marker, a `network` wait writes one with a reason naming the change and does not replace a standing one with a later `until`.
- [x] 4.6 Test: the first line of a failure's message is stored as `reason`, cut to 300 characters, for a `PlannerError` and for any other exception (`<ExceptionName>: <message>`), after `redact_text`, so a value the active set knows is absent from `planned.json`; a refusal still stores the `units` it returned.
- [x] 4.7 Test: a bare `abk replan` prints `waiting for the network since <time>, next try <time> (attempts n/3, not used)` and the model-service form for a waiting record, `given up` followed by the `abk replan --failed` command for a spent one, `failing n/3: <reason>` for a failing one; `abk replan <change>` while the outage is on makes one planner call and prints that the change is waiting and that no attempt was used instead of `the plan failed`, with exit 1; after the outage it plans the change; `--failed` selects a waiting record and `--forget` removes it; `abk status` lists the waiting change by cause.
- [x] 4.8 Add `waiting`, `waits`, `since` and `until` to the plan record and a `waiting` status to `PlanResult`, catch `NetworkUnavailable` and `ServiceUnavailable` in `plan_all` before the generic handler and classify them with the function group 1 uses for a unit's step (lifted out of the step handler so both read it), write the `network` marker as group 3 does, add the due check to `plan_all` and `_needs_planning`, read the pause at the planning gate, store the bounded and redacted `reason` in `_refusal` and the generic handler, and print the waiting states in `_plan_state`, `cmd_replan` and the status.
- [x] 4.9 Document it in `docs/architecture.md` (the planning section: the wait, the due rule, the pause and the stored reason), `docs/cli.md` (`abk replan`: the listing's states, the output and exit for a waiting change, `--failed`), the `abk-pipeline` skill (the plan states and what to run), and fold it into the changelog bullet group 1 added.
