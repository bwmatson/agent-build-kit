## From `adapt-counts-the-units-own-tests/1`

- `_tests_added` in `src/agent_build_kit/pipeline/wiring.py` parses `git diff -U0` output under whatever git config the operator has. Probed in scratch repos: `diff.interHunkContext=10` merges neighbouring hunks and brings back the neighbours this unit removes (`test_below` and `test_far` counted for a one-line edit in `test_edited`); `color.ui=always` and `diff.external` both return `[]`, so the accounting is silently skipped. The last two also affected the old regex, and no git call in the pipeline guards against config today. Pass `--no-ext-diff --no-color --no-textconv --inter-hunk-context=0` on the per-file diff, and pin it with a test that sets `diff.interHunkContext` in the fixture repo.
- `_tests_added` passes each changed path back to `git diff -- <path>` as a pathspec. A path starting with `:` is read as pathspec magic and the file's tests are dropped (probed: `:test.py` returns `[]`). Glob characters in a name can also match more than the one file. Use `:(literal)<path>` or `--literal-pathspecs`.
- `_test_spans` returns `[]` on `SyntaxError`, so a test file the pipeline's interpreter cannot parse on the side being read (for example, syntax newer than the Python abk runs on) contributes no tests at all. The old regex would still have found its added definitions. This fails open, the direction the accounting exists to guard; `_test_bodies` has the same fallback. Fall back to matching `def test_` on the `+`/`-` lines of that file's diff, or log that the file was skipped.
- `_test_spans` and `_test_bodies` in `wiring.py` repeat the same AST walk and span rule (first decorator line to `end_lineno`, `test_` prefix, sync and async). Build `_test_bodies` from `_test_spans` (`for name, lo, hi in _test_spans(source): bodies.setdefault(name, []).append("\n".join(lines[lo - 1 : hi]))`) so the definition of a test's extent lives in one place.
- Several names and wordings still say 'added' although the set now includes tests the unit deleted or edited inside. `_tests_added` could be `_tests_touched`. `_lines_in` returns tests, not lines (`_tests_overlapping`). The comment on `Restacked.old_tests` (`stack_runner.py:334`) and the `ADAPT_PROMPT` line 'These are the tests the previous work added or changed' (`stack_runner.py:360`) should say 'defined, deleted or edited inside'. The prompt matters most: a test the old work deliberately deleted is now listed, cannot be found at `{old_ref}`, and the only passing decision is `retire` with a reason 'in the predecessor', which is not why it went. Add a sentence saying a test the previous work itself deleted is retired with that as the reason.
- In `_adapt` (`stack_runner.py:1299`) the outstanding names are recovered by substring-matching `` `name` `` against the message strings from `check_test_decisions`, so the two are coupled through message wording. A problem that stops backticking its test would silently leave the `outstanding:` line. Have `check_test_decisions` return the test name alongside each problem (or a name-to-problem mapping) and build the line from that.
- In `tests/pipeline/test_wiring.py`, the docstrings of `_spaced_tests` and `test_a_test_only_on_a_context_line_is_not_the_units` say the edit puts both `test_above` and `test_below` in the diff's context. Only `def test_below` is: the insertion is after line 8, so the leading context is lines 6-8 and `def test_above` on line 1 is outside it. The `test_above not in counted` assertion is therefore vacuous as a context check. Either move the edit to the first body line of `test_edited` with `test_above` one blank line closer, or correct the docstring.
- For whoever owns the change: the regex this unit replaces was already anchored on `^\+`, so it matched only added lines, never context or removed ones. The design's premise (context and deleted lines were being matched) does not describe the code that was there. This unit therefore widens the set, newly counting deleted and edited-inside tests as the spec requires, rather than narrowing it. The failure that motivated the change (an old, unrelated test demanded of a unit) probably has another cause, such as a stale `old_base` making the range include work that is not the unit's; with the wider set, such a range would now list more tests, not fewer. Worth confirming before relying on this change to fix that failure.
