# Design

## What was checked, and where

Read-only against agent-build-kit `origin/main` (`d234b00a`, fetched first); paths are under `src/agent_build_kit/` except `web/` and `docs/`. The
research behind this change was done by two read-only agents. Their approach, recorded so it can be repeated: build in-memory graphs from `StoredUnit`

no `abk replan`, `tick` or `requeue`, and touch no unit worktree. The same kind of graphs are what the tests of this change build.

### VERIFIED: where the redundant edges come from

- The planner's prompt asks for them (`PROMPT` 522-531), and `_check_acceptance` and `_check_independent` accept them without needing them: both
  read `_upstream`, which is reachability.
- `plan_units` gives an acceptance or narrow unit `tuple(u.id for u in units)` once an independent group has been seen (222-229). It has no caller in
  `src`; it is a reference the tests use.
- `link_needs` appends a target when `target in unit.depends_on` is false (2362), a direct-membership test, every tick, because `upsert` rewrites the
  list from the plan; it then sets `needs` to the declared targets that are in the linked list (2383).
- In the live store 73 of 352 edges are redundant; the units most affected end in an `[acceptance]` group.

### VERIFIED: what a reduced store does not change

Each was run on in-memory graphs with the real function, and the live store compared unit by unit.

- The base and the open-parent rules of a unit that has not started: `_builds_on`, `unrelated_open_parents`, `second_open_parents` and `_stack_base`
  read reachability through `through_satisfied`, so a dependency another reaches changes nothing.
- A satisfied unit in the middle of a chain, cycle detection (`find_cycle`, `path_between`, the planner's depth-first search, `_upstream`: reachability
  is preserved), the planner's acceptance and narrow validation (it reads `_upstream`), `waiting_on_me` (the reverse walk follows a chain).
- On the live store: `ready_units` at caps 1, 2, 3 and 5, `in_progress`, `uncounted`, `failed_waiting_units`, priority, age and start order are
  identical. Only two units (the acceptance units of two changes) differ at all, in the text of their wait list, and both stay blocked.
- No started unit of the live store has two or more open parents today, so the change in a started unit's base (below) moves none of them.

### VERIFIED: what changes, and what is done about each

1. **A hold on rework.** A grandparent that is planned, running, failed, held or closed while the parent is in review no longer holds a
   never-started grandchild (it becomes ready, as a plain chain's does today), `upstream_incomplete` no longer stops a running one, and an in-review
   one is moved only through the chain. Decision: accepted for ordinary units, which behave as plain chains do. Recreated for acceptance and narrow
   units by a rule computed at run time from the change's units. A closed ancestor no longer stalls its listed descendants for good, which is today's
   worse behaviour.
2. **The base of a started unit** is `listed[-1]` over the in-review same-repo dependencies (`base_of`, 432), which depends on list order, so a
   later `Needs:` ancestor listed last can flip it; `predecessor` (`wiring.py` 2764-2777) takes `parents[-1]` (2777) the same way. A reduced list removes the
   related entries and so the hazard for a chain; for two unrelated open parents the order still decided. Decision: a started unit's base is chosen as
   an unstarted unit's is (`_stack_base`), and `predecessor` is chosen the same way; a test keeps it.
3. **Restack and branch removal.** `_children_of` and `_dependents_of` use direct membership, so a grandchild no longer finds an ancestor as a direct
   parent: the second restack of a child already moved with its parent goes, and a grandchild whose middle unit is in rework is no longer moved
   directly off the leaving ancestor but follows the chain. 29 parents have fewer dependents (one 9 to 2; the count from the research run, not repeated here). The probe of branch removal
   (`events.py` 568) claims fewer units.
4. **A cross-repo wait.** C in repo Y listing A (in the same repo as B), where B waits for A's merge: reduced, C waits for B's merge only. It differs
   only in a state that needs a re-plan or a reopened A after B started. Recorded, not recreated.
5. **`link_needs` and the `needs` mark.** It tests direct membership, so a `Needs:` target the chain implies would be linked again each tick and, once
   reduction removed it, lose its thick edge. Decision: `needs` is its own stored field naming every declared target; `link_needs` tests reachability;
   a target the chain implies draws no edge.
6. **Joins.** `check_joins` refuses on "also waits on A" and "not a line" because of redundant edges; reduced, more joins are permitted, which is a
   correct reading of the line. The repointing of a join de-duplicates and the result is reduced.
7. **Cosmetic.** Planner in-flight lines, the replan "now depends on" lines, the pull request body's "Merge A, B first", the web list and the graph
   show fewer entries.

### VERIFIED: the two gaps in the chain path, which exist for plain chains today

`follow_predecessors` skips a unit whose cause is `restack_deferred` or `restack_conflict` (2985), and a thread that declines the move leaves the
unit in review (a delivery returning false falls to the store write only when there is no thread). A grandchild that depends on this path inherits
both. The spec records them and does not fix them.

### UNVERIFIED

- **The flag on a started record.** `StoredUnit.flag` is set by `set_calibration` for a unit that has not started (`unit_store.py` 730) and kept after;
  300 of 303 live records carry no flag, so a started acceptance unit planned before flags were kept follows the plain chain. Only three records carry
  one today. The group that adds the rule tests that a unit with no flag is treated as a plain chain, and the builder confirms that every planning path
  records the flag (`_record_calibration` is the one caller found) and corrects this item if another path plans a unit without it.
- **"Earlier" for the rule.** The units of a change are numbered in plan order (`<change>/<n>`), and a join deletes a unit, leaving a gap. The rule
  is written as a lower number than the unit's own among the units whose `change` is the same; the builder confirms no path renumbers a started
  change (`replan` was read, not run) and says so here.
- **A unit planned out.** The rule skips `unplanned` units (the plan dropped them); today an edge to one holds its dependent because it is not
  reviewed. The builder confirms from `upsert` (and `drop_cycle_edges`) whether a stale edge to an unplanned unit is cleared on replan, and corrects
  this item.
- **`satisfied_landed`** (`units.py` 532) tests every direct same-repo dependency; reduced, a satisfied unit that listed an ancestor and its child
  tests the child alone, which has merged after the ancestor in any stack. UNVERIFIED for a stack merged out of order by hand; a test pins the
  ordinary case.
- **The one-time reduction on a running tick.** It is written through `set_dependencies` under the store's own lock; whether a unit in a thread's
  hands (a running build holds a copy of its `Unit`) is affected is read from `as_stored` (`wiring.py` 3020), which re-reads the store, so the
  running unit sees the reduced list at its next check. Not run; the test uses a fake store.
- **`web/src/pages.tsx`** renders the server's `depends_on` list as it is, so the web list is changed at the route (`serve/server.py` 304); a web test
  of the rendering was not read and none is added.

## The function

`direct_dependencies(unit, graph) -> tuple[str, ...]`: the units of `unit.depends_on`, in their stored order, that no other unit of that list reaches
through stored `depends_on` edges, walking through units of every state (a merged middle unit still carries its edges) and in every repo, with a
`seen` set so a stored cycle ends the walk. Two units that each reach the other keep both (a stored cycle is reported elsewhere, not reduced). It
does not look through a satisfied unit: `through_satisfied` is the scheduler's lens, and the stored list is a record of what was planned.

Writers call it, readers call it, and nothing else reduces: `upsert` over the merged store, `set_dependencies` over the store with the new list,
the repointing in `join`, and the one-time pass are the only writes; the graph page, the server's `related` list, `abk status`, `_unmerged` in the pull
request body, `_replan_differences` and `in_flight_item` are the readers. A new reader that rebuilt the reduction itself would drift from the others.

## The acceptance and narrow rule

For a unit whose `flag` (read with a default so a plain `Unit` has none) is `acceptance` or `narrow`, `waiting_on` adds each earlier unit of the same
change, in the unit's own repo by the same-repo rule (not in review, merged or satisfied) and in another repo by the cross-repo rule (merged, or
satisfied and landed), exactly the wait an edge to it would have. The rule adds waits only: it does not change `base_of`, `second_open_parents` or
`depth_of`, which read stored edges. `upstream_incomplete` and `follow_predecessors` take the same earlier units as parents for such a unit, so a unit
that has started stops, or leaves review, when one of them goes back. The planner still checks that such a unit reaches every unit it exercises
(`_check_acceptance`), so the stored maximal edges and the run-time rule cover the same units.

## The one-time reduction

At the start of a tick and of `abk replan`, a pass reads the store, computes `direct_dependencies` of each unit with a redundant entry and calls
`set_dependencies` for it, logging `<unit>: dependencies reduced: <removed>`. It is idempotent (a reduced store is untouched, so a second tick does
nothing), never edits `runs/units.json` by hand, and runs after group 1 of this change has made the acceptance rule available: until then the stored
edges are what holds an acceptance unit.

## Direction note: the test kinds are being renamed

Added while this change is in flight; it changes nothing this change specifies. The two kinds of test, today `tier1` and `tier2`,
are being renamed `unit-test` and `e2e-test` so that "tier" can mean how much review a change gets (see the risk-tiered review
design in the framework repository). The change `test-kind-names-are-accepted-both-ways` adds the layer that reads both spellings,
and group 3 and the groups after it wait for it, so they are built with the new names available.

- Names this change's specs fix (a setting, a tag, a metric) are built as the specs write them. The rename carries them; do not
  rename them by hand and do not edit the spec.
- Anything this change is free to name (a helper, a fake, a test file, a local name) uses the new words.
- If a check rejects an old spelling in a directory the rename has already converted, rename that occurrence to the new spelling,
  keep the behaviour the spec describes, and say so in the commit message. A reviewer reads the new spelling as the same setting as
  the spec's old one.
