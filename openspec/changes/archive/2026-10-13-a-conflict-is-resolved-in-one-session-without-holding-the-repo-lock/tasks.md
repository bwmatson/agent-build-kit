## 1. [agent-build-kit] [tier1] The repo's turn is held per phase of a restack, and a unit with no worktree gets a temporary one

Done when a restack takes the repository's turn only for the git commands that write shared state (the rebase up to its stop; the continue or abort, the branch update, the rerere cache write and the temporary worktree's removal; the push), another unit's worktree add and push complete while a blocked fake resolver runs, a branch that moved during the resolver is retried once and then held, a unit with no worktree is moved in a temporary detached worktree without switching the operator's checkout, and the stack-move handler and a unit's own restack in a run follow the same rule. Estimate: about 520 changed lines.

- [x] 1.1 Test: in `tests/pipeline/test_restack_turn_phases.py`, with a fake resolver that blocks on an event, a second thread takes the repository's turn (a `worktree add` and then a push through the real lock file) and completes while the resolver is blocked; and the turn is held, as observed from a third thread's `try_file_lock`, during the rebase start and during the continue, and not between them.
- [x] 1.2 Test: a clean move holds the turn for its git commands only and calls no resolver; a rate limit raised by the resolver aborts the rebase inside the turn, leaves the branch at its old head, and re-raises; an error raised by the resolver aborts inside the turn and raises `RestackConflict`; in none of them is a rebase in progress in the worktree afterwards.
- [x] 1.3 Test: the stack-move handler's restack (through `build_stack_moves`) takes the turn per phase and not around the whole move, and its push still takes the turn on its own; a unit's own `restack_onto` in a run takes it for the same phases (and was not taking it before); neither path takes the turn while holding it.
- [x] 1.4 Test: when the branch ref changed while the resolver ran, the restack aborts and starts again once from its first phase; when it changed again the unit is left `planned` with cause `restack_deferred` and a note naming the branch and both heads, nothing is pushed, and the run's once-per-run hold is not consumed; a remote that moved is still a `StaleRemote` from the push's lease and is not retried.
- [x] 1.5 Test: in `tests/pipeline/test_restack_temporary_worktree.py`, with no worktree for the unit the move is made in a temporary detached worktree made at the branch head under the turn, the repository's own checkout is on the same branch, with the same working tree, before and after, the branch is moved by compare-and-swap under the turn, and the temporary tree is removed under the turn.
- [x] 1.6 Test: a branch checked out in another worktree does not make the rebase refuse in the temporary tree, the branch reference is not moved, the unit is held `planned` with `restack_deferred` naming the checkout, and the temporary tree is removed; a temporary tree left by a stopped restack is aborted and cleared under the turn before the same branch is restacked again.
- [x] 1.7 Split `move_branch_onto` in `pipeline/restack.py` into a start phase (rebase up to its stop, the conflicted and replayed paths, the recorded branch head), a finish phase (the branch head compare, rerere forgets, staging, `rebase --continue`) and an abort, each taking a `turn` context-manager factory (a no-op by default); keep the checks and `Moved` as they are.

## 2. [agent-build-kit] [tier1] A conflict is resolved in one session, smallest change first, and each call is recorded as `restack`

Needs: every-agent-call-is-recorded group 1 — the shared recording helper and the restack ledger node this step uses

Done when the restack's agent step states the order (the conflicting hunks only, then the unit's other files that depend on the conflict, then a port) in its first prompt, runs each step as a call of the unit's build session with the existing checks (no marker, the unit's own tokens present, none of the unit's own tests missing) between them, names a failed check in the next call, names files beyond the conflict among those resolved, keeps every replayed-resolution rule except that a rejection now fails the step instead of aborting the move, runs in the run that finds the conflict and under the usage gate, and writes one `restack` ledger row per call. Estimate: about 500 changed lines.

- [x] 2.2 Test: a first call that leaves one of the unit's own tokens missing gets a second call in the same session whose prompt names the missing token and allows the unit's other files that depend on the conflict; a second call that passes continues the rebase with those other files named among the resolved ones; a first call that drops one of the unit's own tests gets a second call naming the test; a call that edits a file outside the conflict is accepted and named.
- [x] 2.3 Test: a conflict marker left in a conflicted file, after the second call, ends the step with a `RestackConflict` carrying the conflict text and the old tests, as the resolver's failure does today, and the rebase is aborted inside the turn; a rate limit, an interruption and an outage re-raise as before, with the rebase aborted.
- [x] 2.4 Test: a replayed resolution left unchanged is staged by the step after its checks and not by git; one that is edited replaces the cache entry; one that gets a marker has its cache entry forgotten before anything else, fails the call's check, and the step goes on to its second call instead of aborting the move; a restack with replayed resolutions among its conflicts staged each deliberately.
- [x] 2.5 Test: in `tests/graph/test_restack_step_in_prepare.py`, with reuse on the step's first call continues the unit's recorded build session and records `restack` as the last node to speak in it; with no recorded session it starts the build session on the rework model and the next build node continues it; with reuse off, or a session the runtime cannot continue, each call is a new session whose prompt repeats the order and the failed check.
- [x] 2.6 Test: a usage pause defers only the agent step (a conflicting move aborts and waits, a clean move in the same pause proceeds); a conflict found by `verify_base` goes back to `prepare` in the same run, where the step settles it, and `verify_base` makes no agent call; a second conflict in the same run leaves the unit `planned` with cause `base_changed`, and a conflict the step settled does not count as that second one.
- [x] 2.7 Test: in `tests/pipeline/test_restack_ledger_row.py`, a two-call conflict writes two `restack` rows for the unit (change and repo filled, the session id the same on both), a stack move's calls are recorded as `restack` for the child, and the step passes the repository's guard that finds an agent request with no recording.
