# Design

## What was checked, and where

Read-only: `git fetch`, then `git show origin/main:<path>` (origin/main at `d5282e6c`). Paths are under `src/agent_build_kit/`.

- **The lock primitive.** `file_lock` (`pipeline/file_lock.py:25-33`) opens `<path>` for append and calls `flock(LOCK_EX)` with no deadline; `try_file_lock` (36-49) is the `LOCK_NB` form. `e2e.hold_lock` (`pipeline/e2e.py:387-445`) already polls `LOCK_EX | LOCK_NB` every 50 ms against a deadline, and its busy wait is `global_limits.e2e_lock_wait_seconds` (`config.py:737`, default 5400), so the e2e lock is bounded already. `atomic_write_text`/`atomic_write_bytes` go through `_replace_through_partial` (`file_lock.py:52-75`), temporary `<name>.<pid>.tmp`, no fsync. The store, the notifications, the audit, demotion and failure records, the e2e holds and the local forge each lock `<file>.lock` beside the file they guard (`pipeline/unit_store.py:669`, `notify/store.py:29`, `pipeline/audit_record.py:32,41`, `pipeline/demotion_record.py:42,63`, `pipeline/failure_record.py:61`, `pipeline/e2e_holds.py:220,233`, `forges/local.py:101`); `planned.lock` (`cli/pipeline.py:5271`) and `scheduled-e2e.lock` (`pipeline/e2e_schedule.py:112`) are in the state directory.
- **What is machine-local.** `unit_graphs_path(state_dir)` (`graph/checkpointer.py:32-34`) is opened in WAL (`:42`) from `cli/pipeline.py:587, 4171, 4189, 6275, 6329` and `cli/retire_cmd.py:56`. `branch_lock(branch, root=inst.state_dir / "locks")` is an `O_EXCL` pid file (`pipeline/workspaces.py:83-121`), called at `cli/pipeline.py:597, 2822, 5070, 5996` and `cli/retire_cmd.py:125`, read by `lock_holder_gone` and `branch_held` (`cli/pipeline.py:2489, 4161`); the repo lock is `state_dir/locks/repo-<repo>.lock` (`cli/pipeline.py:5322-5326`); the build claim reads `state_dir/locks` (`cli/pipeline.py:4124, 5633, 6285`); `cli/pipeline.py:6951` copies `locks/` into a scratch state. `Leases(lease_dir(inst.state_dir))` is `<state>/leases` (`pipeline/lease.py:20-22`; call sites in `cli/pipeline.py`, `cli/attach.py`, `cli/retire_cmd.py`, `pipeline/attach.py:51`). The e2e lock is `Installation.e2e_lock` = `state_dir / E2E_LOCK_FILE` (`installation.py:99-101`, `model.py:32`) and is also read for `abk status` (`cli/pipeline.py:827`). `environment.lock` is `state_dir / "environment.lock"` (`pipeline/environment.py:349`): it serialises syncing the machine's virtual environments, a local matter.
- **Who judges liveness by pid.** `process_alive` (`pipeline/workspaces.py:54-63`) for branch locks and the e2e record (`pipeline/e2e.py:341, 353, 433`) and the restack lane (`pipeline/restack_lane.py:310`); `Leases._alive` through `/proc/<pid>/stat` (`pipeline/lease.py:25-33, 76-78`) in `take`, `hand_over`, `release_all`, `record_session`, `attachment`.
- **The state's contents.** `docs/architecture.md` "State on disk" (lines 1679-1712) lists every file; `e2e.lock` and `locks/` are one row (1702). `Installation.state_dir` is `_under_root(planning.state_dir)` today (`installation.py:87-89`) and becomes `<planning home>/state` by default with `pipeline-state-lives-outside-the-repo`; `ABK_` settings are `settings.py` fields (`worktree_root`, `settings.py:62-63`, is the model for new ones).
- **Tests available.** `tests/pipeline/test_e2e_lock_*.py` (real `flock` in temporary directories, two handles), `tests/branch_lock_fakes.py`, `tests/cli/in_repo_doctor.py` (`in_repo`, `checks_of`, `named`), `tests/graph/test_checkpoint_*.py`. No `file_lock` or lease test file exists, so the new ones start the files.

## Decisions

### What is local and what is shared

| Path | Owner of the path | Where | Why |
|---|---|---|---|
| `unit-graphs.sqlite` (+`-wal`, `-shm`) | `graph/checkpointer.unit_graphs_path` | local dir | WAL needs shared memory |
| `locks/` (branch locks, `repo-<repo>.lock`, change locks from the sibling change) | `workspaces.branch_lock`, `cli/pipeline.repo_turn`, `task_progress.change_lock` | local dir | pid files and flocks about processes of this host |
| `leases/` | `pipeline/lease.lease_dir` | local dir | a lease names a process of this host |
| `e2e.lock` | `Installation.e2e_lock` | local dir | one queue per host's stack; its record names a pid |
| `environment.lock` | `pipeline/environment.py` | local dir | guards this machine's environments |
| `units.json`, `verified.json`, `planned.json`, `prs-*.json`, `verdicts.json`, usage ledger, the pause files, `notifications.json`, `landing.json`, `audits.json`, `demotions.json`, `held-waiting.json`, `decisions.jsonl`, pages, transcripts, unit logs | their writers, as today | state dir | durable, the point of the share |
| `<file>.lock` beside a shared file (`units.json.lock`, `usage-cache.json.lock`, `planned.lock`, `scheduled-e2e.lock`) | as today | state dir | the lock must sit where every writer of the file can reach it; it is the one the probe vouches for |

The sidecar locks stay beside their files on purpose. They are the locks that protect shared data, so they have to be where the data is, and that is what the probe proves works; moving them local would protect nothing if two hosts did write (which is unsupported anyway) and would split a file from its lock. The locks that move are the ones that guard this machine's processes. The unit-log and transcript directories are large and append-only; they stay in the state directory (they are what a person browses on the share) and are not locked.

`planning.local_dir` follows the other two settings: strongest first `ABK_LOCAL_DIR`, then `abk.local.yaml`, then `abk.yaml` (`abk doctor` warns that a tracked value is a machine fact, like the others, and `doctor._machine_keys` lists it). Absolute or `~`; a relative value is refused (it would be the repository's). Default `<planning home>/local`, so `planning.home` moves it with the rest; a separate planning repo (state stays in `runs/`) defaults it to the state directory so nothing moves for it. `Installation.local_dir` is the one property every site reads; `Installation.e2e_lock` and a new `Installation.locks_dir`/`leases_dir` are defined on it, and `unit_graphs_path` takes the local dir (its parameter is renamed, not duplicated).

### Migration

Nothing in a live installation is lost by being left behind, and one thing is worth carrying:

- `locks/`, `leases/`, `e2e.lock`, `environment.lock` under the state directory are **ignored**, not moved: they are kernel-released or hold only live-process records, and a record left by a crashed process is judged stale on its own. The doctor reports a leftover (`local dir` check, warn) so a person deletes it.
- `unit-graphs.sqlite` is **copied once** to the local dir, on the first open when the local one is absent and the old one exists, through `sqlite3`'s backup API (a consistent copy with the WAL applied, never a file copy of a database another process may hold). The old file is left, the doctor warns that it is stale, and a person removes it. A unit's graph thread therefore resumes where it was.
- A tick running while the install is upgraded can still hold the old paths; the upgrade is a stop-the-timers step in the runbook, as for the sibling changes.

### A bounded `file_lock`

`file_lock(path, timeout=None)` polls `flock(LOCK_EX | LOCK_NB)` every 50 ms (the loop `e2e.hold_lock` has) until `timeout`, which `None` resolves to `settings.lock_wait_seconds` (`ABK_LOCK_WAIT_SECONDS`, default 120). Whatever holds these locks is done in seconds (the module docstring); 120 s is generous for a slow share and short enough that a tick does not outlive its timer's next fire by much. It is an environment setting, not a config key, so no signature gains a parameter at its ~15 call sites. On expiry it raises `LockTimeout` (a `TimeoutError`) whose message names the file, the seconds waited, `ABK_LOCK_WAIT_SECONDS` and the filesystem type of the path. The caller's write is inside the lock, so nothing is half written; the tick's existing handler logs it and the unit or pass fails this tick and is tried the next. Nothing is stolen or deleted on a timeout. The wait is not applied to the e2e lock (it has its own setting) and `try_file_lock` is unchanged. A `flock` blocked in the kernel on a hard-mounted share that stopped answering cannot be interrupted from the process; the poll loop never blocks in the kernel, but an `open` or `read` on such a mount still can, so the doctor's mount report names `hard` mounts and advises `soft,timeo=` or `hard,intr` equivalents for the share (see Risks).

### The probe

`pipeline/lock_probe.py`, `probe_locking(directory) -> ProbeResult`: create `<directory>/.abk-lock-probe-<host>-<pid>`; hold `flock(LOCK_EX | LOCK_NB)` on one handle; start a child interpreter (`sys.executable -I -c`, a wall-clock timeout of 10 s) that opens the same path with its own handle and tries `LOCK_EX | LOCK_NB`; the child prints `blocked` on `BlockingIOError`, `granted` if it got it, `error:<errno>` otherwise. Pass means `blocked`, and the child then succeeds after the parent releases (the lock is released, not stuck). Fail means `granted` (locks are accepted and exclude nothing), `error` (ENOLCK, ENOTSUP: no lock manager) or the timeout. The probe file is removed. The child is a real second process because a second `open` in one process is already a separate holder on a local filesystem, but not necessarily on a share that implements locks per process owner. The injected seam, for tests, is a `spawn` callable defaulting to `subprocess.run`, so a test passes a fake that reports `granted`, `error:37`, a timeout and `blocked`, with a temporary directory as the directory, as `tests/pipeline/test_e2e_lock_*.py` use real handles in temporary directories.

Locks held on one host need only exclude that host's processes, so a mount that implements `flock` locally (`nolock`, `local_lock=all` for NFS; `nobrl` for SMB) **passes** the probe, and is correct on the supported topology. That is why the probe tests exclusion rather than refusing network filesystems by name.

`pipeline/mounts.py`, `mount_of(path) -> Mount(fstype, source, options, local)`: the longest mount point in `/proc/self/mountinfo` that holds the resolved path; `local` is false for `nfs`, `nfs4`, `cifs`, `smb3`, `smbfs`, `9p`, `drvfs`, `fuseblk`/`fuse.*` (sshfs, rclone), `virtiofs`, `vboxsf`, `ncpfs`, `afs`, `ceph`, `glusterfs`. Anything unreadable gives `unknown`, treated as not local (the probe runs). On a system without `/proc/self/mountinfo` the result is `unknown` and says so.

Where it runs:

- `abk doctor`: always, on the state directory (a `state locking` check: ok with the mount type, or FAIL with the detail and fix), plus a `state mount` info line when the state is not on a local filesystem ("durable state on <fstype> <source>: one pipeline host only"), plus a `local dir` check.
- The tick, at its start, **only when the state directory's mount is not local**: the result is cached in `<local dir>/state-lock-probe.json` (mount source, fstype, options, result, time) and re-run when the mount's facts changed or after 24 hours, so a local-disk state pays nothing and a share pays one child process a day. A cached pass is trusted; a fail (cached or fresh) makes the tick print the doctor's detail, write nothing and exit 1 before the planning sync. `abk status`, `abk serve` and read commands do not run it.
- The fix text names the mount type and the choices: for `cifs`/`smb3` mount with `nobrl`; for `nfs`/`nfs4` mount with lock support (`lockd` and `statd` running, no `nolock`) or `local_lock=all`; for `9p`/`drvfs`/FUSE "this filesystem does not provide locks: use a network filesystem with them, or keep `planning.state_dir` local and sync it another way"; and in every case `planning.state_dir` back on a local disk.

There is deliberately **no override** that runs on a share the probe refused: a lost update in `units.json` is silent, and a person who is sure can fix the mount, which is what the message says.

### Atomic writes

`_replace_through_partial` names the temporary `<name>.<host>.<pid>.tmp` (`host.this_host()`, the machine name with characters outside `[A-Za-z0-9._-]` replaced), fsyncs it (`os.fsync` on a handle opened on the finished file) before `os.replace`, and fsyncs the directory after, ignoring an `OSError` there (several remote filesystems refuse a directory fsync). A rename that raises `PermissionError` or an `OSError` with `EBUSY` is retried up to 5 times with 0.1 s, doubling, then raised: SMB refuses a rename over a file another client has open, and the other client closes in moments. Whatever is raised the temporary is removed and the old file stays, as now. Writers on two threads still share a name and hold the file lock, as the docstring says; the host in the name only matters to the foreign-writer case that is unsupported, and costs nothing.

### Holders know their host

`pipeline/host.py`: `this_host()` and `is_here(record_host)` (an empty or missing host is here: records written before this change belong to the one host that wrote them). The records gain a `host` field: the lease (`Leases.take`, `hand_over`, `lease.py:107-158`), `branch_lock`'s JSON (`workspaces.py:116`), `LockRecord` (`pipeline/e2e.py:287`, an optional field with a default so an old record parses). A record whose host is not here is **live by definition**: `Leases._alive`, `process_alive`'s callers (`lock_holder_gone`, `branch_lock`, `branch_held`, `restack_lane.py:310`, `e2e` messages) answer from the record, not from `/proc` or `kill`. `branch_lock` raises `BranchBusy` naming the host; `Leases.take` returns False and `Attachment` shows `host` and `stale=False`; the e2e wait message names the foreign host and says its process cannot be checked from here. A person whose other host is really gone removes the record by hand (the message says which file). With the locks local and one host, this path is never taken; it is there so a `local_dir` pointed at a share by mistake, or a second host started by mistake, fails closed rather than stealing.

## Risks

- **Lock failure is silent.** A filesystem that accepts `flock` and excludes nothing makes every read-modify-write racy and nothing logs it. That is why the probe refuses, rather than warns, and why the tick checks it where a doctor run is not enough. The probe proves two processes of this host exclude each other on this mount; it does not prove another host would be excluded, which the topology rules out.
- **SMB rename over an open file** fails with `EACCES`/`EBUSY` (a reader on another client, a backup tool, an indexer): the bounded retry covers a moment, and a persistent failure raises with the path, the write is not retried silently for ever.
- **Power loss leaving a zero-length file.** Without fsync a rename can reach the disk before the data, so the final name holds an empty or torn file. The fsync before the rename closes that; the stores that read JSON already treat a torn read as a retry (`pipeline/unit_store.py:1064`), and the doctor does not repair a file that is already empty.
- **A hard-mounted share that stops answering** blocks any `open`/`read`/`write` in an uninterruptible state; no timeout in this process can end it, so the bounded lock wait protects against a share that answers slowly and holds locks, not against one that hangs the kernel call. The documented mount advice (`soft` with a `timeo`, or `intr` semantics where the kernel still has them) is the mitigation, and the timer's own next fire is not blocked by the previous one (the tick takes its own lock).
- **A stale probe cache.** A share remounted with other options between a daily probe and the tick is caught because the cached key includes the mount's source, type and options; a share whose server changes behaviour without a remount is caught the next day or by `abk doctor`.
- **Migration copy.** The old SQLite is copied once and left; a person who deletes the new one and keeps the old gets the old copy again, which is the stale state the doctor warns about.

## Out of scope

- Two hosts running ticks, timers or `abk serve` against one state directory. `units.json` is a read-modify-write of one file under a lock that, on a share, may exclude only this host's processes; two schedulers would double-start units whatever the locks do. This change makes the one-host case correct and makes a foreign host's records safe to meet, and nothing more; the documentation says the first plainly.
- Moving the unit worktrees, the pipeline worktree or the data home to the share.
- A distributed lock or lease service.
- Backing up the shared state.
