# Design

## What was checked, and where

Read-only against agent-build-kit `origin/main` (`7e04c86`); paths are under `src/agent_build_kit/`.

- `graph/nodes.py` `prepare` returns `"e2e-test": unit.tier == "e2e-test"` (about 958); `after_review`, `after_unit_test` and the `approved` branch of
  `after_prepare` route to `Node.E2E` on it; `after_e2e` routes to `VERIFY_BASE` (or `NEW_COMMENTS` after a move). Nothing routes a unit that
  has no commits to e2e-test: `after_prepare` sends it to `TESTS` (an agent writes tests), then `IMPLEMENT`, and the only road to `SATISFIED` is
  `after_unit_test` on `produced_nothing`, which e2e-test never follows. `unit.tier` is `e2e-test` when any carried group is tagged `e2e-test`
  (`pipeline/units.py` about 239); an `[acceptance]` group is always `e2e-test` and gets no other treatment in the node.
- `graph/nodes.py` `e2e-test` (about 1626): `ok, snapshot = r.run_e2e(cwd=..., base=base)` first; on failure it reads `r.e2e_verdict()`, parks through
  `wait_for_preexisting` when every failure is pre-existing, otherwise saves feedback and stops. A passing run returns the snapshot, and the status
  is posted later by the `push` node (`post_status`), so a unit that never pushes posts none.
- `pipeline/wiring.py` `E2eSession.run(cwd, base)`: when the repo has the dev stack script, `_run_on_dev_stack` runs the script's `up`, `test` and
  `down` and returns (no profile command, no ids, no classification). Otherwise it builds `toolchain.e2e_commands(where, marker=...)` for each
  project, takes the stack lock once inside `_locked()` around every command, parses failures, and calls `_judge`. `_judge` returns None when
  `limits.e2e_base_runs` is 0 or the run passed; otherwise `classify` calls a failure the unit's own when its file is among the files changed
  against the base (`_changed_files`: `git diff --name-only <base>...HEAD`) or sits beside a changed `conftest.py`, and every other failure is
  untouched and run once on the base in a detached worktree. On a tree equal to its base nothing is changed, so every failure is untouched and the
  base run happens: it would not be skipped by itself.
- Unit-test's list of the tests a unit added or changed is `touched_tests(tree, ref)` (`wiring.py` about 2619): `(file, test)` pairs from a comparison of
  each changed source file's test bodies against `ref`, a deleted test left out. `repeat()` (unit-test, about 997) turns them into identifiers relative to
  each project (`_under`) and asks `toolchain.repeat_command(command, ids)`, the `RepeatsTests` hook of `profiles/base.py`: the command's options
  (workers, markers) stay, its paths are replaced by the ids that fall under them, and it returns None when none does. A profile without the hook
  has no repeat check. `serial_rerun_command`, which the research for the earlier changes pointed at, is the wrong tool for this: it drops the
  command's markers and workers and selects by identifier whatever the markers are. `repeat_command` keeps the marker, so a changed test without
  the e2e-test marker is deselected and the run collects nothing, which `no_tests_collected_exit` already treats as no failure.
- The `e2e_commands` of the shipped profile with the live-stack tests is one command per member that has tests, with the marker and the summary and duration flags; the node
  profile's is not implemented, so e2e-test runs only through a profile with the hook today.
- `pipeline/untouched_failures.py`: `ensure_fix` writes the change into `inst.changes_dir` under `preexisting.lock` and calls no git: nothing in the
  pipeline commits an autogenerated change; it sits as files in the planning repository until a person commits it. `wait_on_preexisting` adds the
  `Needs:` line to each group of each member of the unit through `add_needs_to_unit` and the tasks file's own lock. `open_fix_change` /
  `next_fix_name` read the changes directory and `changes/archive/*-<name>`; a change is open while its directory is under `changes/`.
- `pipeline/archive.py` `is_ready_to_archive`: a unit in `SATISFIED` counts once `satisfied_landed` holds (no same-repo dependency, or each has merged),
  and `verify_change` returns a pass without running anything when no unit of the change has merged with a pull request. So a change whose only
  unit ends satisfied archives on its own. `openspec archive <change> --yes` accepts a change with no `specs/` directory (tried against the
  installed CLI, which only warns about the proposal's headings).
- `cli/pipeline.py` `cmd_tick` returns at once when `has_work` is false, before any usage read or planning; `has_work` is true for a unit in
  progress, a satisfied unit awaiting verification, or a change whose `tasks.md` is not planned in its current form. `run_round` plans
  (`plan_all`, a model call) only when `_may_build` admits, behind the usage guard. `_preview_fixes` prints the fix changes of recorded failures on
  `--dry-run` before the `has_work` return.
- `config.py` `limits`: `unit_test_repeat_runs`, `restack_check` (a `StrEnum`, `RestackCheck`), `e2e_base_runs`, `e2e_lock_wait_seconds`,
  `max_units_in_progress` (5). `tests.e2e_marker` (default `local_stack`) is a field of every repo, so it does not say whether a repo has an e2e-test
  suite. `abk config --show` prints the whole effective config; `abk doctor` reports no `limits` value today.

## Where the settings live

Each setting is a pair: a global default under `limits` (`limits.e2e_unit_scope` `own`, `limits.e2e_schedule` `weekly`) and an optional override on
the repo's `tests:` block (`TestsConfig`, beside `e2e_marker`), `repos.<name>.tests.e2e_unit_scope` and `repos.<name>.tests.e2e_schedule`, both
`None` when unset. The value in effect for a repo is the repo's when set, otherwise the `limits` one, through one function used by every reader.

- **The schedule is per repo** because what it controls is a suite that belongs to a repo: whether one has a live suite worth running every week, how long
  it takes and how often it breaks differ by repo. The due date, the open scheduled change and `off` are all per repo, so one repo can run weekly
  while another is `off`. A global default keeps a one-line setup for an installation with one habit.
- **The scope is decided by the same reasoning.** Whether a unit's own tests are enough is a property of how coupled that repo's tests are to shared
  fixtures and helpers, which `touched_tests` does not see; a repo with such coupling wants `full`, the rest `own`. It is also the repo's `tests`
  block that already names the marker the scope narrows. So a repo overrides a global default here too.
- `tests:` is read per repo already (`RepoConfig.tests`); `limits` is installation-wide. Nothing else moves. An override of `off` is the YAML
  boolean problem described below, handled the same way in both places.

## Per-unit scope

The scope of a run is decided once, by one function the e2e-test step asks before it takes the lock: `own` or `full`, with the ids and the reason.
`E2eSession.run` uses it, and the gate of `tier2-waits-on-open-base-failure-fixes` asks the same function, so the two cannot disagree about
whether a run executes a failing test.

1. A scheduled unit is `full`: it has no commits and the suite is its work. This rule belongs to group 3; group 1 builds the function with the
   other rules, which the open-fix gate needs, and group 3 adds this one, so the gate holds a scheduled unit with no code of its own.
2. The repo's `e2e_unit_scope` in effect (see above) being `full` is `full`.
3. A repo that runs e2e-test through its dev stack script is `full`. The script's `test` takes no ids and the run exists to test deployment changes a unit
   makes without adding a test, so it is not narrowed, and the log says `e2e-test runs whole: the repo's dev stack script runs it`.
4. Otherwise `touched_tests(cwd, base)` gives the unit's tests; the ids are made as unit-test makes them and each project's command is built by
   `repeat_command`. A profile without the hook, a list that cannot be read (unit-test logs and goes on; e2e-test runs whole, since a pass that
   checked nothing is worse than a long run), and a `base` of None are `full`, each with its reason in the log.
5. When no project's command takes an id, the scope is `own` with nothing to run: the step says `e2e-test skipped: no e2e-test test added or changed`,
   takes no lock, and returns a result with zero tests that its snapshot labels as run on no tests. An e2e-test command that is built and collects
   nothing (the changed tests lack the marker) is the same outcome, found after the run. The pull request status the unit posts for such a result
   says that no e2e-test test ran, not that the suite passed.

An own run is the unit's own by construction: every id it ran is a test the branch added or changed, and `classify` already calls a failure in a
changed file the unit's own. The base run and the record are therefore reached only by a `full` run (or by a scheduled run, below); the code
path is not touched. A change to a helper module, a fixture or shared test data is not seen by `touched_tests` (it says so in its own docstring)
and so does not select the tests that use it; the schedule is what catches such a break, which is the trade the setting buys. `full` is there for a
repo that wants the old behaviour.

## The schedule

**Which repos.** A repo is scheduled when the unit store holds a unit of it whose `tier` is `e2e-test` (the store never drops units). A repo with no
e2e-test unit has no suite the pipeline knows of; `tests.e2e_marker` always has a value and cannot tell.

**Name and due date.** `scheduled-e2e-<repo>-<YYYY-MM-DD>`, the date being the day it is written (UTC). The last scheduled run of a repo is the
latest date among the directories `changes/scheduled-e2e-<repo>-*` and `changes/archive/*-scheduled-e2e-<repo>-*`, read from the name; a
suffix that is not a date, or a name for a repo whose name merely begins with this one's, is not matched, because the repo is compared whole after
the prefix and the date is stripped. Due is the last date plus one day (`daily`), seven (`weekly`) or thirty (`monthly`) at or before today, or
no earlier change at all, each read with the repo's schedule in effect. One open change per repo, found by a directory under `changes/` with the prefix, so a change that is waiting on a fix, failed
or running keeps the next from being written, and a missed week is one change, not two. `off` for a repo does nothing at all for that repo.

**Where it runs.** In `run_round`, in a step before `plan_all`, under a lock file in the state directory (`scheduled-e2e.lock`) so that two ticks
write one change, as `preexisting.lock` does. Writing the change is a few small files and no model call; planning it is the usual `plan_all`, behind the
usage guard, so a refused window delays the plan and nothing piles up (the open change keeps a second from being written). `has_work` is true when a
repo is due, so an idle installation reaches the round; it reads a directory listing and the store and costs no usage read. While a repo is due and
the guard refuses, ticks are not idle; that ends when the change is written, which does not need the guard, so it is a single tick.
`abk tick --dry-run` prints `would write: <name>` or `exists: <name>` for each scheduled repo and writes nothing, as `_preview_fixes` does.

**The change.** `proposal.md` (why, what changes, impact: all fixed text naming the repo and the date), a short `design.md`, `tasks.md` and no
`specs/`. `tasks.md` holds `Acceptance: none — the run of the suite is the check; nothing a consumer sees changes.`, then one group
`## 1. [<repo>] [e2e-test] Run the full e2e-test suite on the default branch` with `Priority: 3`, a `Separate:` line (so the planner never carries it onto another
unit or another group onto it: a scheduled unit must have no work of an agent's), a `Done when` line and one unchecked task `1.1 Run the whole e2e-test
marker on the default branch and record any failing test`. The change is not committed (like every autogenerated change).

**The unit.** The planner turns the group into a unit (`e2e-test`, priority 3). Whether a unit is scheduled is read from its change's name prefix, a
constant beside the name function, as `fix-failing-` names its changes; nothing is added to `tasks.md` syntax. For such a unit:

- `prepare` goes to `Node.E2E` before looking at feedback or commits. It does not enter `tests`, `implement`, `checks` or `review`, makes no agent call and
  opens no pull request; a rework note left on it by a failure is not acted on.
- `E2eSession.run` is given the unit's scope `full`. Because the tree has no commit against its base, `_judge` makes every failure it names a
  pre-existing one and runs nothing on the base: a base run would be the same tree, command and stack. With `limits.e2e_base_runs` 0 it returns no
  verdict, as for any unit, so a failure fails the unit and nothing is recorded; a failure no test id can be read from has no verdict either and fails it.
- On a pass the node ends the unit with the existing satisfied outcome (`satisfied`: state `SATISFIED`, the tasks ticked, no pull request to close),
  with the note `scheduled e2e-test passed: <n> passed, <m> skipped on <sha>`. The node after e2e-test routes there for a scheduled unit instead of to
  `verify_base`. The change then verifies trivially and archives through the existing path.
- On a failure whose every named test is pre-existing, `wait_for_preexisting` does what it does for any unit: `ensure_fix` writes (or finds) one
  `fix-failing-*` change per test, the unit's group gains `Needs:` lines, and the unit parks `planned`, `gated`, with a resume requeue. When the fix's
  unit is in review (same repo) or merged, `release_gated` resumes it at the e2e-test node, and the whole marker runs again on a tree that has the fix.
  A fix of another repo's test cannot happen: the scheduled change is one repo's.
- Everything else is the ordinary unit: `max_units_in_progress` counts it, the e2e-test lock wait holds it as `tier2-lock-wait-holds-the-unit` says, `abk status`
  lists it with its state and the existing lock line, a failure shows as any failed unit, and `abk requeue` works. The gate of
  `tier2-waits-on-open-base-failure-fixes` holds it too when it is not a unit of the open fix and does not wait on it, because a scheduled run is
  `full`: running the suite into a failure that is already being fixed is the cost that gate exists to avoid.

## Other rules

- **Settings.** Both are `StrEnum`s validated where they are set, in `limits` and in `tests` (an unknown value is refused when the config loads, naming the setting and the values). The
  `off` of a schedule is a YAML 1.1 boolean when unquoted; the loader accepts `false` as `off`, as `checks.affected.mode` does, and the docs show it quoted.
- **A repo with no scheduled name collision.** A hand-made change that happens to begin with the prefix is treated as scheduled by its unit; the
  prefix is reserved and the docs say so.
- **Archived names.** `openspec archive` prefixes the archive directory with the day it ran, and the scheduled name keeps its own date inside, so the due
  date is the date the change was written, not archived.
- **Existing recorded failures and fixes** are read and written as before when the schedule is `off`; the setting only stops new scheduled changes.
- **Not part of this change:** giving the failed e2e-test units a `Needs:` on group 1, and rework notes for them.

## UNVERIFIED

- Whether the tree of a unit with no commits is at the default branch's current tip each time `prepare` runs (the unit's worktree is made at a base
  ref; whether that ref is refreshed first for a unit that never pushes). The builder confirms the scheduled run fetches the default branch before
  it runs and corrects this document; the spec requires the run to be on the tip as of its start.
- How the planner treats a group that asks for no code: whether it sizes or warns on it, and whether `Separate:` is enough to keep it alone. The
  builder runs the planner on the written change in a test with a fake model and, if it objects, changes the text, not the rule.
- The wording of the posted status for a run of no tests (`e2e_post_status` in `pipeline/e2e.py`): the spec fixes that it says no e2e-test test ran;
  the builder fits the sentence to the existing description.
- Whether a unit parked at the e2e-test node whose tree is a scheduled unit's can be restacked onto the fix's branch by the existing release (the
  restack code is written for units with commits). The builder confirms the resumed unit's tree has the fix and, if the restack refuses an empty
  branch, creates the unit's tree on the fix's branch directly.
- Whether the status of a satisfied unit with no `pr` prints cleanly in `abk status` with the note above (a satisfied unit with no pull request is
  ordinary, but this one has run e2e-test). The builder reads the status output and corrects the note's form.
- `abk doctor` shows no limits value today, so "shown by doctor" is not claimed; `abk config --show` prints the effective config and so shows both
  settings with no code. Whether a doctor line is wanted is left to a later change.

## Direction note: the test kinds are being renamed

Added while this change is in flight; it changes nothing this change specifies. The two kinds of test, today `unit-test` and `e2e-test`,
are being renamed `unit-test` and `e2e-test` so that "tier" can mean how much review a change gets (see the risk-tiered review
design in the framework repository). The change `test-kind-names-are-accepted-both-ways` adds the layer that reads both spellings,
and group 4 and the groups after it wait for it, so they are built with the new names available.

- Names this change's specs fix (a setting, a tag, a metric) are built as the specs write them. The rename carries them; do not
  rename them by hand and do not edit the spec.
- Anything this change is free to name (a helper, a fake, a test file, a local name) uses the new words.
- If a check rejects an old spelling in a directory the rename has already converted, rename that occurrence to the new spelling,
  keep the behaviour the spec describes, and say so in the commit message. A reviewer reads the new spelling as the same setting as
  the spec's old one.
